## Project Overview

Marketing website for Merzouga desert tours built on Astro 5 with TypeScript, multilingual support (English, French, Spanish), and a booking system. Based on the Odyssey Theme framework with extensive customizations for tour content.

## Development Commands

### Local Development
```bash
cd frontend
npm install
npm run dev              # Dev server at http://localhost:3000
```

### Docker Environment
```bash
docker-compose up --build
# Astro dev: http://localhost:3000
# MailDev UI: http://localhost:1080 (SMTP on port 1025)
```

### Other Commands
```bash
npm run build            # Production build to frontend/dist
npm run preview          # Preview production build locally
npm run format           # Format with Prettier
npx astro-i18next generate  # Generate localized page copies after route changes
```

## Architecture

### Internationalization (i18n) System

**Key insight:** This project uses `astro-i18next` with a **file-based routing approach** where localized pages are physical copies in language subdirectories.

- **Config:** [frontend/astro-i18next.config.cjs](frontend/astro-i18next.config.cjs) defines locales (en/fr/es) and namespaces (common/home/tours/footer/gallery/contact/about). Add new namespaces here as well as creating the JSON files.
- **Translations:** JSON files in [frontend/public/locales/{locale}/{namespace}.json](frontend/public/locales/)
- **Page structure:**
  - Default locale (en): [frontend/src/pages/](frontend/src/pages/) (e.g., `index.astro`, `tours/index.astro`)
  - Other locales: [frontend/src/pages/{locale}/](frontend/src/pages/) (e.g., `fr/index.astro`, `es/tours/index.astro`)
  - Each localized `.astro` page calls `changeLanguage("fr")` (etc.) in its frontmatter, then reads `i18next.resolvedLanguage` to pass `locale` down to components.
  - `landing-pages/` exist only under `fr/` and `es/` (no English version).

**Workflow when adding/modifying routes:**
1. Create or update the default English page
2. Update translations in all locale JSON files
3. Run `npx astro-i18next generate` to create/update localized page copies
4. Verify all three languages have matching routes

### Tour Content System

Tours are **MDX files** in [frontend/src/pages/tours/posts/](frontend/src/pages/tours/posts/) using the [Post.astro](frontend/src/layouts/Post.astro) layout.

- **Each tour exists three times**, hand-translated: `pages/tours/posts/*.mdx` (en), `pages/fr/tours/posts/*.mdx`, `pages/es/tours/posts/*.mdx`, with identical filenames. The translated copies are full rewrites (body + frontmatter), not generated by `astro-i18next generate`. When editing a tour, update all three.
- Localized copies are one directory deeper, so their `layout` path is `'../../../../layouts/Post.astro'`.
- [frontend/src/utils/tours.ts](frontend/src/utils/tours.ts) `getTours(locale)` loads every tour via `import.meta.glob('../pages/**/tours/posts/*.mdx')`, infers locale from the path, and sorts newest `publishDate` first. Listing pages and the home slider use this.
- Tour bodies are structured with `<div id="overview">`, `<div id="highlights">`, `<div id="itinerary">`, etc. (anchors used by `TourNav`) and use tour components such as `TourHighlights`, `TourItinerary`, `TourInclusions`, `TourFAQ`, `TourMap` from `@components/odyssey-theme`.

**MDX frontmatter structure:**
```yaml
---
layout: '../../../layouts/Post.astro'
title: 'Tour Title'
description: 'SEO description'
publishDate: 'YYYY-MM-DD'
featuredImage: '/assets/images/tours/...'
excerpt: 'Short summary'
price: 'From €X per person'
duration: 'X days / X nights'
mapUrl: 'https://www.google.com/maps/d/.../embed?mid=...'  # optional, used by TourMap
tags:
  - 'Tag1'
  - 'Tag2'
---
```

**Important:** Tour MDX files can import and use Odyssey Theme components:
```jsx
import { Button } from '@components/odyssey-theme';
```

### API Endpoints

Two server endpoints (`prerender = false`, POST only), both sending mail via Nodemailer with SMTP config from env vars (see [frontend/.env.example](frontend/.env.example); `BOOKING_MAIL_TO` is the recipient):

- [frontend/src/pages/api/book.ts](frontend/src/pages/api/book.ts) - tour booking. Requires `firstName`, `lastName`, `email`, `tour`, `people`, `phone`, `startDate`, `endDate`. The booking form in `Post.astro` lazy-loads `PhoneInput.js` and `DateRangePicker.js`.
- [frontend/src/pages/api/contact.ts](frontend/src/pages/api/contact.ts) - contact form. Requires `email` and `message`.

Both use an in-memory per-IP rate limit (5 requests / 15 min), which resets on cold start.

### Other Content

- Home-page reassurance section content lives in [frontend/src/content/reassurance/](frontend/src/content/reassurance/) as `{en,fr,es}.mdx`; only the frontmatter is imported by `ReassuranceSection.astro`. The section embeds TripAdvisor's free "ratings only" widget (`cdsratingsonlynarrow`, no API key) and restyles its injected markup via `:global()` rules. The paid TripAdvisor Terra API was evaluated and dropped: it bills every call and forbids caching.
- `WhatsAppButton.astro` is a floating button rendered from `Base.astro`; its tooltip text comes from the `whatsapp.tooltip` translation key. Pass `whatsapp={false}` to `Page.astro`/`Base.astro` to hide it (done in `Post.astro`, where it covered the tour booking bar).
- `BookTourButton.astro` is the floating "Book your tour" button, added to the three homepages only (label: `bookCta.label`). On phones it becomes a bar docked to the bottom edge and lifts the WhatsApp button above it.
- Company pages (about/contact/legal) are under `pages/company/`.

## Important Patterns

### Translation Workflow
When adding translatable content:
1. Add English text to appropriate namespace in `public/locales/en/{namespace}.json`
2. Add French translation in `public/locales/fr/{namespace}.json`
3. Add Spanish translation in `public/locales/es/{namespace}.json`
4. Keep JSON structure identical across all three files

### Working with Tours
- New tour: Create the MDX file in `tours/posts/`, `fr/tours/posts/` and `es/tours/posts/` with the same filename
- Images: Place in `frontend/public/assets/images/`
- Tags: Used for tour categorization and filtering
- Layout: Always use `Post.astro` layout with relative path from post location

### Email Testing (Local Development)
The Docker environment includes MailDev for catching all outgoing emails:
- All emails sent via the booking endpoint are captured
- View emails at http://localhost:1080
- No real emails are sent in local development

## Build & Deployment

- **Output:** Static site in [frontend/dist/](frontend/dist/)
- **Adapter:** Vercel (configured in [astro.config.mjs](frontend/astro.config.mjs))
- **SSR:** Only `/api/book` and `/api/contact` require server mode; rest is static
- **Site URL:** `https://www.truemoroccotours.com`, set in `astro.config.mjs` and `src/config/settings.js`; used for canonical tags, the sitemap (with hreflang alternates) and JSON-LD. Keep it on www: Vercel serves www and redirects the bare domain to it.
- **Assets:** Hosted from [frontend/public/](frontend/public/)
- `frontend/.github/workflows/deploy.yml` (Deno Deploy) and `netlify.toml` are leftovers from the Odyssey Theme, not the actual deploy target.
- There is no test suite or linter; `npm run build` is the main correctness check.
- **URLs have no trailing slash** (`trailingSlash: 'never'`): canonicals, sitemap, hreflang and internal links all use `/fr/tours`, and Vercel 308-redirects `/fr/tours/` to it. Keep every URL in that form.
- Pushing to `main` deploys to production on Vercel.

## SEO & Google Search Console (after every push)

The owner tracks indexing in Google Search Console (Domain property, owner access shared with the client). **After every `git push`, end the reply with a short "Search Console" note** saying what, if anything, to do there for what was just pushed. Write it in French, as concrete clicks with the exact URLs (www, no trailing slash, every affected locale).

1. Wait for the deploy, then check the live pages that changed: title, meta description, canonical, and 200/308/404 status. The `www` CNAME (at Namecheap, which hosts the DNS) points to `cname.vercel-dns.com`, because the project-specific Vercel target's IPs time out on the owner's mobile network. If a check times out, retry with `curl --resolve www.truemoroccotours.com:443:76.76.21.21 ...`.
2. Pick the actions that match the change:
   - **New tour or page:** URL inspection → "Demander l'indexation" for the en/fr/es URLs. Google allows about 10 requests a day, so list the most important ones first.
   - **Changed title, description, H1 or main content:** request indexing of that page in each locale.
   - **Deleted or renamed page:** a 404 is fine for a page that is gone. If it was renamed or has a clear replacement, suggest a redirect to it.
   - **Site-wide URL or SEO plumbing** (site URL, trailing slash, canonical, hreflang, robots.txt, sitemap, redirects): resubmit `https://www.truemoroccotours.com/sitemap-index.xml` under Sitemaps. Then click "Valider la correction" on the affected reasons in the Pages report.
   - **Nothing SEO-related** (styles, Docker, tooling): say that there is nothing to do in Search Console.
3. Point out any SEO weakness spotted in the pushed pages: a missing or generic `seo` title or description, a title over ~60 characters, a description over ~155 characters, or a locale left untranslated.

Every page passes its own `seo` (`title`, `description`) to `Page.astro`, from a `seo` key in its locale namespace (e.g. `home:seo.title`). `settings.js` only holds the fallback.
